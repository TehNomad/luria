# Milestone 5h: the CLI's documentation

Status: **Ready for the worker, 2026-10-18.** Planner: Claude. Parent:
[docs/tasks/contracts/milestone-5-cli.md](/tasks/contracts/milestone-5-cli.md) §5 (5h) and §6 (the pinned example).
Follows 5g3.

## 1. What and why

The `luria` executable exists and is tested end to end, but there is no
[docs/specs/cli.md](/specs/cli.md): `luria help` already points to it. Plan §5 gives 5h three
deliverables: [docs/specs/cli.md](/specs/cli.md), README usage and the product brief's status.
Plan §6 adds that the planner hand-writes one expected document in
[docs/specs/cli.md](/specs/cli.md), and a test checks the CLI's output against it field by
field.

**Scope, as the owner set it on 2026-10-18:** [docs/specs/cli.md](/specs/cli.md) holds the worked
example, the `luria version` document and short reference tables: commands,
exit codes, error codes, and the request and result at a glance. The longer
reference prose — every template rule, every request field, every result
field — is left for the owner to write, and the page says so in its last
section. Until then plan §3.3–§3.5 is the authority for those details.

**Every file this contract adds or changes has its content given below, or
in the page file it names.** The worker's job is to place it exactly, write
the one new test, run the checks, and carry out §8's proofs. This contract
adds no production code: if a test cannot pass without changing
`crates/*/src/`, stop and report it.

### 1.1 One deviation from plan §6

Plan §6 asks for the pinned example to be "a synthetic case". 5g3 §1.1
established that no CLI request can carry the synthetic design templates:
a run needs a complete CDS, and those 100-base templates have none. The
example is therefore the SID-1 D404N edit, the repository's one real
template, where every scientific value is already in an independently
verified fixture (§3).

## 2. Requirements this contract applies

- **Plan §6:** the expected document is hand-written, not produced by
  running luria, and a test compares the CLI's output with it field by
  field.
- **AGENTS.md:** fixture expectations are never generated by running the
  implementation. §3 names the source of every value in the example.
- **Plan §3.5:** floats print in shortest round-trip form and are never
  rounded. The example therefore cannot state exact float bytes: the real
  document prints `-373.2999999999999`, not `-373.3`. The page writes the
  verification tables' own precision instead, says so in §3 of the page,
  and §7's test compares those fields within a tolerance.
- **D041 G10:** "The limit is stated in [docs/specs/cli.md](/specs/cli.md) and the README":
  no circular template can be designed.
- **D020 and the product brief:** a result is a computational claim, never
  experimental validation.

this contract.

What it does:

1. Read `../../docs/specs/cli.md` as a string. Extract the two fenced JSON
   blocks by their marker comments: the block whose fence follows
   `<!-- luria:request -->`, and the one whose fence follows
   `<!-- luria:result -->`. A block is the lines strictly between the
   ```` ```json ```` line and the next ```` ``` ```` line, joined with
   `\n`, with one `\n` appended. If either marker or fence is missing,
   panic naming which.
2. Build a workspace under `CARGO_TARGET_TMPDIR`, as the other CLI tests
   do. Copy `../../tests/fixtures/example-construct/input/sid-1_cDNA.fa`
   into it, and write the request block's bytes to `d404n.json` there.
3. Run the `luria` binary as `q5 design d404n.json` in that directory, the
   way `end_to_end.rs` does. Assert the exit status is 0.
4. Parse the binary's stdout and the page's result block with
   `luria_cli::json::parse_json`, and compare them field by field as §7.1
   says.

### 7.1 How the comparison works

Use `luria_cli::json::parse_json`, **not** `serde_json::Value`. This
workspace does not enable serde_json's `preserve_order`, so a
`Value::Object` is a sorted map and a key-order check over it cannot fail
(worker, 2026-10-18; enabling the feature would be a dependency change,
which §10 forbids). `parse_json` returns `Json::Object(Vec<(String,
Json)>)` and keeps members in document order, which is why
`result_design.rs` already uses it for exactly this purpose. Its numbers
are `serde_json::Number`, so the integer and f64 rules below are unchanged.

Write one recursive comparison over `luria_cli::json::Json`:

- **Objects:** the same key set, in the same order. Compare each value.
  Report the JSON path of any difference: a missing key, an extra key, a
  different order, or a different value.
- **Arrays:** the same length, element by element.
- **Strings, booleans and nulls:** exactly equal.
- **Numbers:** if both are integers, exactly equal. Otherwise compare as
  f64 within the tolerance for the path, from this table:

  | Path ends with | Tolerance |
  | --- | --- |
  | `celsius`, `annealingTemperature` | 0.005 |
  | `gcPercent` | 0.005 |
  | `enthalpyKcal` | 0.05 |
  | `entropyCal` | 0.05 |
  | anything else | 0.0, i.e. exactly equal |

  `monovalentMillimolar`, `primerNanomolar` and `dmsoPercent` are floats
  whose page values are exact, so the 0.0 default is right for them.

The tolerances exist only because the page states the verification tables'
precision and luria prints full precision (§2). Do not widen one to make a
field pass: a field outside its tolerance is a real disagreement, and §7.3
says what to do.

### 7.2 Also assert

These may use `serde_json::Value` for the lookups, since no key order is
at stake:

- `document["provenance"]["requestSha256"]` equals the SHA-256 of the
  request block's bytes, computed in the test with
  `luria_core::identity::sha256_hex`. This proves the page's digest
  describes the page's own request text, and is the one field whose value
  the page could otherwise state freely. The page's literal digest must
  equal it too, so compare all three.
- `luria version`'s stdout parses, and its `algorithms` array equals the
  `provenance.algorithms` array of the result, element for element. The
  page prints the two in two places and they must agree.
- The result's `experimentalValidation` is `"not_performed"` and its
  `state` is `"verified"`.

### 7.3 If the CLI and the page disagree

**Stop and report, with the path and both values.** Do not edit
[docs/specs/cli.md](/specs/cli.md), do not widen a tolerance, and do not change the test's
expectation. The page is a hand-written expectation under plan §6, and a
disagreement is either a planner error in the page or a defect in the CLI.
Either way it is the planner's to resolve, not the worker's.
