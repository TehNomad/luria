# Product brief

Status: Initial draft
Date: 2026-10-02
Working name: Molecular Biology Toolbox

## Purpose

Build a standalone molecular-biology toolbox that combines reliable
sequence-based tools with a natural-language interface.

Users should be able to describe an operation in ordinary language,
inspect how the application interpreted it, resolve ambiguity, and
receive reproducible results calculated by validated software.

The long-term goal is a broad toolbox. Development starts with one
well-defined workflow rather than implementing many incomplete tools.

## Intended users

- Molecular biologists and protein scientists working with constructs,
  plasmids, coding sequences, and mutations.
- Users who want a convenient interface without writing scripts.
- Advanced users who want reproducible inputs, machine-readable outputs,
  and clear provenance.

The interface should support expert review without requiring users to
understand the application's internal architecture.

## Initial reference workflow

Given a DNA construct with a defined target CDS, interpret a request
to design primers for a series of independent amino-acid substitutions
using the NEB Q5 site-directed mutagenesis workflow.

Example user request:

"Using this plasmid, design Q5 SDM primers for A42G and W87A as separate
variants. Number residues from the beginning of the annotated CDS."

The application should:

1. Identify the input construct and target CDS.
2. Interpret the requested mutations and whether variants are separate
   or combined.
3. Validate the original residues against the translated CDS.
4. Resolve missing or ambiguous information before design.
5. Record the DNA changes and replacement codons.
6. Generate candidates using an explicitly supported design method.
7. Validate the intended edited construct independently of candidate
   generation.
8. Present sequence context, primers in 5'-to-3' orientation, calculated
   properties, warnings, and provenance.
9. Allow export of the reviewed result.

Combined multi-mutant constructs are a distinct request. They must not
be silently treated as independent variants or assumed to use the same
supported design workflow.

## Scientific trust model

The LLM interprets language and explains structured results.
It is not the source of truth for sequence calculations.

Deterministic code is responsible for:

- Coordinate conversion.
- Strand handling and reverse complementation.
- CDS extraction and translation.
- Mutation validation and sequence editing.
- Primer calculations and supported workflow constraints.
- Verification of the resulting edited sequence.

The application must distinguish:

- A requested operation.
- A calculated result.
- A warning or unresolved assumption.
- Computational validation.
- Experimental validation.

A calculated design must not be presented as experimentally validated
unless supporting experimental evidence has actually been supplied.

## Required inputs

An operation must declare which inputs it needs.

The initial Q5 workflow requires the DNA template needed for the
supported plasmid-based design, an identified target CDS, a numbering
convention, and explicit mutation intent.

A protein sequence alone is insufficient for this workflow because
it does not establish the actual template DNA sequence.

Missing information must produce a clarification request or structured
error rather than a plausible invented result.

## Architecture direction

- Rust provides domain models, validation, application orchestration,
  and user-facing application components.
- Python workers provide selected scientific computations where useful.
- Rust and Python communicate through a versioned, typed contract.
- Frontends call the same application capabilities rather than duplicating
  scientific logic.
- Pi is a development tool, not a runtime requirement.
- Runtime operations are explicit, typed capabilities, not arbitrary
  shell commands generated by an LLM.

Start with a core library and automated tests.
Add a minimal CLI to exercise complete workflows when appropriate.
Build the TUI first, then a web interface over the same application logic.

## Initial implementation milestone

Implement the sequence, feature, CDS, and coordinate foundation.

Required outcomes:

- Explicit linear and circular sequence topology.
- Explicit strand and coordinate semantics.
- Validated extraction of supported CDS representations.
- Translation under an explicitly declared supported genetic code.
- Known-answer tests for ordinary and edge-case inputs.
- Structured errors for invalid or unsupported input.

This milestone does not include LLM integration, Python workers, primer
design, persistence, a TUI, or a web interface.

## Subsequent milestones

- Mutation interpretation and deterministic edit validation.
- Versioned Rust-Python worker communication.
- Q5-specific candidate generation and validation.
- End-to-end reviewable results and exports.
- Natural-language parsing into typed requests.
- TUI, followed by web access.

Reorder these milestones only through an explicit scope decision.

## Future capabilities

Potential additions include sequence conversion, translation, construct
analysis, general primer design, assembly planning, and other validated
molecular-biology operations.

These are roadmap candidates, not first-release commitments.

## Non-goals

- An autonomous wet-lab scientist.
- Automatic ordering of oligos or execution of external actions.
- Experimental success guarantees.
- A generic chat interface that produces unverified sequence outputs.
- A dependency on Pi for end users.
- Distributed job infrastructure or multi-agent orchestration at launch.

## Privacy and reproducibility

Scientific operations should run locally where practical.

Cloud use must be explicit. Private constructs, sequences, credentials,
or experimental records must not be sent to a cloud model by default.

Results should record sufficient inputs, versions, parameters, and
assumptions to reproduce the calculation.

## Definition of success

The first complete workflow succeeds when:

- The interpreted request is visible and reviewable.
- Invalid or ambiguous requests fail clearly.
- Scientific results can be obtained without an LLM.
- Known-answer and negative tests pass.
- The intended edit is verified against the complete supported template.
- Results expose assumptions, warnings, and calculation provenance.
- A user can understand and export the result without using a coding
  agent.
